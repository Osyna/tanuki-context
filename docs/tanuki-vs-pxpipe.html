field report · 2026-07-26 · all figures measured, scripts in-repo

Same engine.
Different contract.

pxpipe proved that pixels are cheaper than tokens, and its imaging engine is genuinely good; good enough that we ported it glyph-for-glyph. This report is about the part we couldn't keep: the transparent proxy. We ran it, measured a real 76.5% input-token cut, and then watched a security-conscious agent refuse its own configuration because a rewriting proxy is indistinguishable from an attacker. tanuki-context keeps pxpipe's renderer and replaces the proxy with explicit MCP tools the model calls on purpose. Below: what that trade costs, what it buys, and the numbers for both sides.

01 · credit first

What pxpipe got right

The core insight is theirs and it holds: an image's token cost is fixed by pixel dimensions, not by how much text is inside it. Their README claims ~3.1 chars per image-token on real Claude Code traffic and 18.4 chars per vision-token for a dense page. We reproduce the dense-page figure exactly; under the 28-px patch pricing they adopted in v0.11 (and we adopted the same week) a full 1568×728 page is 56×26 = 1,456 tokens, which puts the same page at 19.3 chars per vision-token. Their correction made everyone's pages 4–5% cheaper. Good fix.

We didn't rebuild their renderer, we extracted it. Page geometry, the Spleen 5×8 atlas, reflow, wrapping, page splits: byte-faithful. When upstream repainted the confusable K glyph (their A/B: K→H misreads went 42→1), we regenerated our atlas from their build the same day. The benchmark in this repo drives both renderers on identical files: 25/25 parity rows pass against pxpipe v0.11.0's own code. So when we say "same engine" it's not a figure of speech. The disagreement is entirely about who decides what gets imaged.

02 · the disagreement

A transparent proxy has a structural problem

pxpipe sits between your agent and the API and rewrites requests in flight. To image the system prompt it has to move it somewhere a vision block can live, so it lands in a user-turn wrapper:

The relocated prompt arrives labelled <system-reminder> … not written by the user. That is, almost word for word, what a prompt injection looks like. One of our agents read its own rewritten request, flagged it, and refused to proceed. It was right to. From inside the model there is no way to tell a helpful rewriting proxy from a hostile one.

This isn't a bug pxpipe can patch. It's what "transparent" means. The same silence has a second cost: the model never gets to say no. If it needs to quote a hash or a config line back exactly, tough; the proxy already imaged it. pxpipe mitigates with gates and skip-reasons, but the model, the one party that knows what it needs, isn't consulted.

tanuki's answer is boring: make it a tool call. The model runs tanuki_estimate (geometry only, never touches pixels, safe to call on everything), reads an exact verdict, and renders only when the pipeline wins. Nothing is rewritten behind anyone's back. The system prompt stays where the API put it.

pxpipe: implicit

Proxy rewrites every request. Zero client integration. Covers system prompt, tool docs, history. Model can't opt out, and can't tell the rewrite from an attack.

tanuki: explicit

MCP tools the model calls per payload. Needs an MCP client and model cooperation. Can't touch the system prompt. Everything imaged was chosen, estimated, and decodable.

03 · what the tool contract buys

Two stages pxpipe doesn't have, then the same pixels

A proxy has to be fast and safe on arbitrary traffic, so pxpipe images more or less what it receives. A tool gets handed a specific payload with intent, and that changes what you can do before pixels. tanuki distills logs first (repeated lines collapse to one exemplar plus a count; near-dupes fold into templates; error and warn lines are never touched), then optionally compresses prose on a 5-level ladder with an exact-recall guard for code, hashes and paths. Character cuts multiply through pixel cuts, which is where the numbers get silly.

One real 200 KB journal log (1,623 lines), this machine, this week:

raw text
51,168 tok
imaged (pxpipe path)
10,752 −79%
distill → imaged
6,160 −88%
distill + codebook + tiny
2,576 −95%

Imaging alone gets −79%. The stages in front more than double it. All 272 error/warn lines verbatim in the output; distill reported 1,624 → 890 lines. Reproduce: npx tanuki-context estimate <log> 2 --distill --codebook --font tiny

On top of distill sit three density knobs, all off pxpipe's parity path, all reversible or legend-decodable. Measured against the shared imaging baseline (level 0, patch pricing):

Corpora: this repo's README (prose), src/main.ts (code), a 400-line path-heavy synthetic log. The full table prints on every bun test run; 9 tests assert the floors, the pack round-trip, codebook reversibility, and append-stable pages.

One more thing a proxy can't easily justify but a tool can: tiny payloads. pxpipe's page is always full-width, so a two-line error costs a full-width row of patches. tanuki's pack trims page width to the widest actual row. A 70-char error line: 17 tokens as text, 56 as a full-width image, 13 packed. The verdict flips, and estimate is how you find out for free.

05 · the numbers game

Read both headline claims carefully

pxpipe's README leads with "~59–70% lower end-to-end bill." Ours could lead with "−95% on a journal log." Both are true and both are marketing until you name the denominator. Their number mixes workloads and includes cache pricing effects; our −95% is one log with every knob on. The honest comparables:

  • Imaging alone, identical input: identical by construction. 25/25 parity, same pixels, same patch count. Nobody wins this row, which is the point.
  • Real traffic, proxy mode: 76.5% input-token cut. That's pxpipe's own event log on our traffic, counted against a free count_tokens counterfactual. It's a good number. It's also the number an earlier stats script inflated to 99.6% by ignoring 6.5M cache-read tokens, which is why every figure in tanuki now names what it's divided by.
  • Log-shaped payloads, tool mode: −88 to −95% total. No proxy equivalent exists because the stages that do it (distill, codebook) need to know what the payload is.

Their context-window chart ("1M tokens → ~19M chars imaged") is arithmetic on the same density we share, so we have no quarrel with it. If anything the tiny font extends it: at 32.1 chars per vision-token the same 1M-token window holds ~32M characters, with the stated 99.7% read-back caveat attached.

06 · so which one

Pick by who you trust to decide

Run pxpipe when you can't touch the client and want the whole request compressed, system prompt included, and you accept a rewriting middlebox in your API path to get it. Nothing else does that job.

Run tanuki-context when your agent speaks MCP and you want the model to choose: estimate first, render when it wins, distill logs before they ever become pixels, and keep every transform decodable from the page itself. You give up system-prompt coverage; you get back consent, selectivity, and two extra compression stages the proxy can't reach.

They also compose. tanuki upstream of the API, pxpipe in front of it, nothing conflicts; the engines are the same code lineage and now share the same token model. Our position, since an agent already voted with its refusal: the imaging belongs in the open, where the model can see what's being done to its own context.
